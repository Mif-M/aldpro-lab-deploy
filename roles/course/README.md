# Ansible-роль для подготовки лабораторного стенда KVM/libvirt

Проект содержит Ansible-роль, которая автоматизирует развертывание лабораторного стенда для прохождения **профессионального курса по программному комплексу [ALD Pro](https://www.aldpro.ru/professional/aldpro.html). Курс посвящен администрированию рабочих мест под управлением ОС Astra Linux в домене ALD Pro и включает практические задания по развертыванию контроллеров домена и рабочих станций в натированной сети.

Роль разворачивает стенд на базе KVM/libvirt в Astra Linux: устанавливает необходимые пакеты, создаёт libvirt storage pool и виртуальную сеть, загружает шаблонную ВМ из реестра, расширяет её корневой раздел, клонирует Linux-машины, выполняет очистку уникальных данных и настраивает гостевые ОС через скрипты, добавляет записи в `/etc/hosts` и создаёт стартовые снимки.

**Примечание:** Раздел с Windows-ВМ в текущей версии роли закомментирован и не выполняется. При необходимости его можно включить, раскомментировав соответствующие таски в `tasks/main.yml`.

---

## Требования к оборудованию

Для развертывания тестового стенда рекомендуется использовать хост со следующими минимальными характеристиками:

| Компонент | Минимальные требования |
| --- | --- |
| **Процессор (CPU)** | Не менее 4 ядер (рекомендуется поддержка аппаратной виртуализации Intel VT-x / AMD-V) |
| **Оперативная память (RAM)** | От 16 ГБ |
| **Жесткий диск (SSD)** | От 250 ГБ свободного места |
| **Операционная система** | Astra Linux (оперативное обновление 1.8.4 или более свежее) |

> **Примечание:** Указанные требования являются минимальными для тестового стенда без реальной нагрузки. Для промышленного использования ориентируйтесь на официальные рекомендации ALD Pro.

## Что делает роль

Основной сценарий находится в `tasks/main.yml` и выполняет следующие этапы:

1. Записывает название курса в `/etc/course`.
2. Устанавливает KVM/libvirt и вспомогательные пакеты (включая `libguestfs-tools` для работы с гостевыми дисками).
3. Добавляет административного пользователя в группы libvirt.
4. Перезапускает `firewalld`.
5. Публикует ярлык `virt-manager` для flydesktop.
6. Настраивает storage pool `labs` из XML-файла `pool-labs.xml`.
7. Настраивает виртуальную сеть `ALD-Pro` из XML-файла `net-ALD-Pro.xml`.
8. Загружает шаблонный диск из реестра (`vm.registry`) в каталог `vm.src_dir`.
9. Создаёт (при необходимости) диск большего размера в пуле с помощью `qemu-img create` и расширяет корневой раздел через `virt-resize`.
10. Регистрирует шаблонную ВМ из XML-файла `template.xml`.
11. Для каждой Linux-ВМ из списка `vms`:
    - клонирует диск и регистрирует ВМ с помощью `virt-clone` (таски в `clone_vm.yml`);
    - задаёт максимальное и текущее количество vCPU и объём RAM через `virsh setvcpus/setmem`;
    - выполняет `virt-sysprep` для удаления уникальных данных шаблона;
    - применяет гостевой скрипт настройки сети (`customize_vm_network.sh.j2`) через `virt-customize` с включённым сетевым доступом;
    - применяет гостевой скрипт локальной настройки (`customize_vm_local.sh.j2`) через `virt-customize` без сети.
12. Настраивает PXE-порядок загрузки для тестовой ВМ (`pxe_vm_name`), если она зарегистрирована.
13. Создаёт (с перезаписью) стартовые снимки для каждой Linux-ВМ.
14. Добавляет записи Linux-ВМ в `/etc/hosts` хоста-гипервизора.

## Требования

Роль рассчитана на запуск с повышенными привилегиями на хосте Astra Linux, который будет выполнять роль гипервизора.

На целевом хосте должны быть доступны:

- пользователь-администратор, указанный в переменной `administrator`;
- systemd-службы `libvirtd`, `firewalld` и сетевые службы Astra Linux;
- каталог с исходными артефактами (`vm.src_dir`) – он будет создан автоматически;
- доступ к реестру (URL из `vm.registry`) для скачивания шаблонного диска;
- достаточное свободное место в `disk_dir` (по умолчанию `/labs`) для дисков ВМ.

Пакеты KVM/libvirt устанавливаются самой ролью:

- `astra-kvm`
- `python3-libvirt`
- `python3-lxml`
- `qemu-system`
- `libvirt-clients`
- `libvirt-daemon-system`
- `libguestfs-tools`

## Быстрый старт

1. Установка Ansible
Если Ansible ещё не установлен на управляющей машине, выполните:

На Astra Linux:

bash```
sudo apt update
sudo apt install ansible
```

Проверьте установку:
bash```
ansible --version
```
2. Подготовка окружения
В репозитории уже присутствует файл ansible.cfg с настроенными параметрами (например, пути к ролям, timeout, логирование). Убедитесь, что вы находитесь в корневой директории проекта при запуске, чтобы конфигурация подхватилась автоматически.

Также в проекте есть init.yml – вспомогательный playbook, который может выполнять начальные действия, такие как:
установка дополнительных коллекций (например, community.libvirt);
создание инвентарного файла (если он отсутствует);
проверка доступности целевых хостов.

Если вы используете этот playbook, запустите его перед основной ролью:

bash```
ansible-playbook -i inventory.yml init.yml
```
Примечание: init-playbook.yml не является обязательным и может отсутствовать в вашей версии проекта. Если он есть – ознакомьтесь с его содержимым перед запуском.

Пример playbook для подключения роли:

```yaml
---
- name: Настройка локальной рабочей станции
  hosts: localhost
  vars_files:
    - vars/course.yml
  become: true
  roles:
    - { role: 'course', tags: 'course' }

```

Запуск:

```bash
ansible-playbook init.yml
```

> Если каталог роли называется иначе, укажите фактическое имя каталога в секции `roles`.

### Переменные для Linux-ВМ (`vms`)

Каждая ВМ в списке `vms` может содержать следующие поля (обязательно только `name` и `ip`):

```yaml
vms:
  - name: "dc-1"
    ip: "10.0.1.11"
    domain: "ald.company.lan"      # опционально
    vcpus: 4                       # опционально
    ram_mb: 4096                   # опционально
    netmask: "255.255.255.0"       # опционально
    gateway: "10.0.1.1"            # опционально
    iface: "eth0"                  # опционально
    dns_servers:                   # опционально
      - "10.0.1.11"
      - "10.0.1.1"
    dns_search: "ald.company.lan"  # опционально
    repos:                         # опционально (переопределяет default_repos)
      - "deb https://..."
```

Если поле не указано, используется соответствующее значение `default_*`.

## Storage pool и виртуальные сети

Описание storage pool задаётся переменной `pool`:

```yaml
pool:
  name: "labs"
  file: "pool-labs.xml"
```

Описание виртуальных сетей задаётся списком `network`:

```yaml
network:
  - name: "ALD-Pro"
    file: "net-ALD-Pro.xml"
```

XML-файлы должны находиться в каталоге `files/`. Роль копирует их на целевой хост и регистрирует через `virsh pool-define` и `virsh net-define`. При повторном запуске существующие объекты не считаются ошибкой.

## Шаблон, исходные файлы и Linux-ВМ

В отличие от предыдущей версии, шаблонный диск **скачивается из реестра** по URL, указанному в `vm.registry`. После скачивания в каталог `vm.src_dir` роль:

1. Проверяет, существует ли уже диск в пуле (`/{{ pool.name }}/{{ vm.template }}`). Если нет, или его виртуальный размер меньше `vm.new_size`, создаётся новый диск большего размера с помощью `qemu-img create`.
2. Затем выполняется `virt-resize` для расширения указанного раздела (`vm.partition`) до нового размера.

После этого диск регистрируется как шаблонная ВМ (`template_vm`) с использованием `template.xml`.

**Важно:** утилита `virt-resize` требует, чтобы исходный диск находился в `vm.src_dir`, а целевой – в пуле. Роль копирует (фактически создаёт новый) диск в пул.

ISO-образы в текущей реализации **не используются** – они были удалены из процесса.

## Настройка Linux-гостей

Для каждой клонированной ВМ выполняются следующие операции:

1. **Клонирование диска и регистрация** – через `virt-clone` (подробности в `clone_vm.yml`).
2. **Установка ресурсов** – через `virsh setvcpus` и `setmem` (сначала максимальные значения, затем текущие) с опцией `--config`.
3. **Очистка уникальных данных** – `virt-sysprep -a <диск>`.
4. **Применение гостевых скриптов** через `virt-customize`:

   - **`customize_vm_network.sh.j2`** – выполняется с сетевым доступом и отвечает за:
     - настройку APT-источников (репозитории из переменной `repos`);
     - конфигурацию `resolvconf` (DNS и search domain).
   - **`customize_vm_local.sh.j2`** – выполняется без сети и выполняет:
     - установку hostname и FQDN;
     - запись в `/etc/hosts`;
     - отключение NetworkManager;
     - создание статической конфигурации `/etc/network/interfaces` с параметрами (IP, маска, шлюз, интерфейс);
     - перегенерацию SSH-ключей.

Оба скрипта генерируются из шаблонов с подстановкой переменных для конкретной ВМ.

## Windows-ВМ (временно отключено)

В текущей версии роли блок создания и настройки Windows-ВМ **закомментирован** и не выполняется. Соответствующие таски можно найти в `tasks/main.yml` под комментарием `# Блок 6`. Если требуется включить поддержку Windows, необходимо:

- раскомментировать блок;
- убедиться, что в каталоге `win_src_dir` присутствуют диски вида `<name>.<win_domain>.qcow2`;
- подготовить XML-файлы в `files/` с именами `<name>.<win_domain>.xml`.

## Идемпотентность и повторный запуск

Роль содержит проверки для безопасного повторного запуска:

- storage pool и сеть не считаются ошибкой, если уже существуют;
- шаблонный диск создаётся/расширяется только при необходимости (проверка размера);
- клонирование Linux-ВМ пропускается, если диск уже существует (через `clone_vm.yml`);
- настройка ресурсов выполняется каждый раз (изменения фиксируются);
- `virt-sysprep` и `virt-customize` запускаются при каждом прогоне (они идемпотентны по своей природе);
- снимки удаляются и создаются заново (с перезаписью), чтобы гарантировать актуальность;
- PXE-настройка применяется только если тестовая ВМ зарегистрирована.

Некоторые команды libvirt всё ещё помечаются как изменившие состояние (`changed_when: true`), потому что сами утилиты не всегда дают удобный признак изменения. Это ожидаемое поведение текущей роли.

## Типовые проблемы

### `virt-clone` не находит шаблон

Проверьте, что шаблонная ВМ зарегистрирована под именем из `template_vm`:

```bash
virsh dominfo template
```

### Не удаётся скачать шаблон из реестра

Убедитесь, что:

- URL в `vm.registry` доступен с хоста;
- в `vm.src_dir` достаточно места;
- указаны правильные учётные данные (если требуется).

### Ошибка `virt-resize`: `No such file or directory`

Убедитесь, что исходный диск существует в `vm.src_dir` и целевой каталог (`disk_dir`) создан. Проверьте права доступа.

### PXE-настройка пропускается

Роль ищет ВМ по имени `{{ pxe_vm_name }}.{{ default_domain }}`. Если она не зарегистрирована, будет выведено предупреждение, и шаг пропущен.

### Ошибки доступа к libvirt

Проверьте, что пользователь из `administrator` добавлен в нужные группы и перелогинен:

```bash
id sa
```

### Не хватает места в пуле

Убедитесь, что в `disk_dir` достаточно свободного места для всех дисков и снимков.
